# Account Diagnosis

作为主 Agent 处理账户问题时的操作指南。根据用户当前问题和必要的对话上下文，调用最少且足够的账户 MCP，直接生成面向用户的 Markdown。

只处理问题中的账户相关部分。问题同时涉及基金、市场、策略或其他领域时，不阻止主 Agent 使用其他适用能力。

## 处理账户问题

### 1. 确认账户问题

本 Skill 处理四类账户问题：

| 用户想了解的内容 | 场景 |
| --- | --- |
| 账户有多少资产、由哪些账户构成 | 资产总览 |
| 持有哪些产品、资产和行业如何分布 | 资产结构 |
| 赚了多少、收益率、回撤和分时段收益 | 收益明细 |
| 收益由谁贡献、亏损由谁造成 | 收益归因 |

按问题复杂度分别处理：

- 单一问题，明确对应一个场景 → 直接调用对应工具，直接回答，不需要额外分析。
- 2～3 个意图清晰的复合问题（如“我今年赚了多少？现在买了什么？”）→ 合并处理，进入下一步构思回复与取数计划。
- 开放式或模糊的诉求（如“帮我诊断一下账户”“账户体检”“看看我的账户怎么样”）→ 用户未指定具体想看什么，需要深入思考应覆盖哪些场景、如何组织结论，而不是逐条机械回答或不加选择地调用全部 MCP（取数范围见第 3 节，回复组织方式见第 6 节）。

问题不属于以上四类场景时，本 Skill 不适用，交由主 Agent 使用其他适用能力处理；问题同时包含账户和其他领域内容时，由主 Agent 统一处理，本 Skill 只提供账户数据相关的回答。

如果问题不需要使用用户账户数据，不调用账户 MCP。

### 2. 构思回复与取数计划

单一问题直接进入下一步选择对应 MCP，不需要额外规划。

多个意图组合出现时，按叙事逻辑组织回复顺序，而非用户提问的原始顺序或逐条罗列：

1. 资产总览（有多少、由哪些账户构成）→ 先明确基本盘；
2. 收益表现（赚了多少、走势如何）→ 再说明结果好坏；
3. 资产结构（持仓、行业、地区分布）→ 再解释由什么构成；
4. 收益归因（谁贡献、谁拖累）→ 最后解释为什么会有这个结果。

用户只问及其中 2～3 项时，按上述顺序取其涉及的部分组织语言，不需要为未涉及的项目补充内容。

开放式诉求（如账户体检、账户诊断）中，用户未指定具体想看哪几项。调用 MCP 前先判断：围绕本次诉求，大致遵循以上顺序讲清楚哪几层就够了。不必四层都展开，也不要机械地全查一遍再堆砌。

如果初步取数后发现某一层数据缺失或结论方向需要调整，可以补充取数或简化该层表述，不需要为此再向用户确认。

这一步只决定“打算按什么顺序说、说到哪几层”，具体工具和参数仍按下一步执行。

### 3. 按所需事实选择 MCP

选数依据是第 2 步确定的事实清单，不是用户问句中的关键词或场景名称。

按以下步骤选择：

1. 列出第 2 步确定要回答的事实项（如“总资产”“持仓占比”“今年收益率”）；
2. 对照下表，找到能提供该字段的 MCP；
3. 一个 MCP 已覆盖多个所需事实时，只调用一次，不为表中重叠的其他工具重复取数；
4. 事实分布在多个 MCP、且没有单一工具能同时覆盖时，才组合调用；互不依赖的调用可以并行。

#### 资产总览

| MCP | 中文能力 | 主要返回字段 |
| --- | --- | --- |
| `queryAssetsTotal` | 账户总资产和账户构成 | `totalAmt` 总资产、`holdCnt` 持仓数量、`classifyVoList[]` 账户分类、`sourceList[]` 资产来源、`itemList[]` 产品明细，以及今日/持有/累计收益 |
| `queryAssetIndex` | 今日账户表现 | `yield` 今日收益率、`profit` 今日收益、`excessYield` 今日超额收益、`yieldStatus` 收益状态 |
| `queryHoldingSignal` | 今日持仓提醒 | `positiveCount` 正向信号数量、`watchCount` 关注信号数量、`positive[]` 正向提醒、`watch[]` 关注提醒及相关产品 |

#### 资产结构

| MCP | 中文能力 | 主要返回字段 |
| --- | --- | --- |

#### 收益明细

| MCP | 中文能力 | 主要返回字段 |
| --- | --- | --- |
| `queryProfitAnalyzeSum` | 账户收益总览 | `profit` 收益、`totalYield` 总收益率、`balanceProfit` 持有收益、`redeemedProfit` 已兑现收益、`todayActualProfit` 今日实际收益、`todayEstimatedProfit` 今日估算收益、`status` 数据状态 |

| MCP | 中文能力 | 主要返回字段 |
| --- | --- | --- |
| `queryProfitAttribution` | 产品收益贡献和拖累 | `profit` 总收益、`earnProfit` 正贡献、`lossProfit` 负贡献、`topList[]` 主要贡献项、`bottomList[]` 主要拖累项、`status` 数据状态 |

#### 常见字段重叠时的取舍

- 只需要“总资产是多少”这类总览数字 → `queryAssetsTotal` 已包含粗粒度的今日/持有/累计收益，通常不必再调 `queryProfitAnalyzeSum`；
- 需要收益率、超额收益、最大回撤等更专业的收益分析 → 用 `queryProfitAnalyze`，不用 `queryAssetsTotal` 里附带的粗略收益字段代替；
- 只问“今天表现如何” → 优先 `queryAssetIndex`，它专门给出超额收益和收益状态，比 `queryAssetsTotal` 附带的今日收益更专用；
- 已从 `queryAssetsTotal` 或 `queryHoldingDetail` 拿到持仓分类/数量，且问题不需要产品级占比或明细 → 不再调用另一个持仓类工具。

表中字段来自当前项目资料，只用于理解工具的大致数据范围。实际工具名称、参数、字段和可用能力以运行时 MCP Schema 为准。

## 4. 输出与示例

### 输出原则

- **先回答问题，再补充依据**：第一句直接给出用户询问的结果；只有数据支持时，才进一步说明表现特征。
- **只使用已取得的事实**：只列对当前回答有直接作用的数字，不展示无关字段，也不使用尚未查询的数据。
- **判断必须有依据**：只有存在明确基准、阈值或可比数据时，才使用“跑赢”“集中”“波动较大”等判断；否则只描述客观分布和变化。
- **语气沉稳中性**：客观陈述账户事实，不制造焦虑，不使用“赶紧冲”“赶紧跑”等表达。
- **说明数据状态**：数据处于估算、计算中、部分缺失或不可用状态时，说明它对当前答案的影响，不自行补值。
- **不替用户作投资决策**：缺少投资目标、期限和风险承受能力时，不判断账户是否适合用户，也不直接给出买卖或调仓建议。

### 示例 1：开放式诊断

用户说：“帮我看看账户。”

> 截至 8 月 6 日，账户总资产约 128.6 万元，共持有 12 只产品。今年以来收益率为 5.68%，同期沪深 300 涨幅为 3.12%，账户跑赢基准 2.56 个百分点。
>
> 当前权益类资产约占 63%，固收和现金类约占 37%；行业分布主要集中在科技和消费。科技相关产品是本期主要收益来源，新能源和港股相关产品对收益形成了一定拖累。
>
> 以上结论基于当前账户数据。由于缺少您的投资目标、投资期限和风险承受能力，暂不判断这一结构是否适合您，也不形成调仓建议。

只有实际取得总资产、持仓结构、收益、基准和归因数据时，才能生成对应段落。缺少其中一层时，省略或简要说明数据缺失，不用其他数据补写。

### 示例 2：单一收益问题

用户说：“我今年赚了多少？”

> 截至 8 月 6 日，账户今年以来累计收益为 4.32 万元，收益率为 5.68%。

只回答收益金额和收益率。除非用户同时询问是否跑赢、回撤或分阶段表现，否则不额外查询和展开这些内容。

### 示例 3：资产结构问题

用户说：“我的钱都怎么分配的？”

> 账户总资产约 128.6 万元，当前主要分布为：
>
> - 权益类基金：约 81 万元，占 63%；
> - 固收类及专户：约 32 万元，占 25%；
> - 现金类资产：约 15 万元，占 12%。
>
> 从现有数据看，权益类资产占比最高；行业分布主要集中在科技和消费，区域上以 A 股为主。

没有正式阈值或用户风险信息时，只描述主要分布，不判断配置是否合理或是否符合用户风险偏好。
