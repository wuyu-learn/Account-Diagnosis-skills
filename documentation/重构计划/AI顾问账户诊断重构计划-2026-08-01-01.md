# AI 顾问账户诊断重构计划

计划日期：2026-08-01

计划次序：第一阶段（账户诊断基础架构重构）

## 1. 计划目标

基于当前项目 Markdown 形成的账户路由、结果编排、卡片数据和复杂诊断规则，重构 `account-diagnosis` Skill。

本次重构主要处理 `account-diagnosis`。全局入口 `route-extract` 的场景分类和实体抽取逻辑保持不变，但上游分发协议需要增加原始用户问题的原样透传，避免账户域只收到拆分后的 `subQuery`。

重构目标：

```text
上游大模型负责理解用户
→ 输出任务复杂度、卡片计划和卡片参数

代码负责确定性拼接
→ 生成业务 Section、卡片结构、顺序和固定字段

按任务复杂度调用不同大模型任务
→ 简单任务生成 Summary
→ 复杂任务生成 Summary + Conclusion

代码负责最终合并和校验
→ 输出 v2.2 JSON
```

## 2. 依据文档

- [`AI 顾问账户路由.md`](../AI%20顾问账户路由.md)：简单/复杂任务定义及账户域调度；
- [`AI顾问复杂账户诊断输出.md`](../AI顾问复杂账户诊断输出.md)：复杂任务的诊断逻辑；
- [`AI顾问结果输出与组件编排.md`](../AI顾问结果输出与组件编排.md)：最终 Section/Card 结构；
- [`AI顾问账户卡片与数据.md`](../AI顾问账户卡片与数据.md)：卡片、参数和 MCP 数据边界；
- [`AI顾问整体架构.md`](../AI顾问整体架构.md)：账户诊断在全局系统中的位置。

`account-diagnosis` 必须保持独立和自包含。实施时需要将必要规则精简后放入 Skill 的 `references/`，不能在运行时依赖 `documentation` 目录。

## 3. 重构前实现的问题

### 3.1 所有任务固定生成 Conclusion

当前 `SKILL.md`、`references/result-composer.md` 和 `scripts/compose_result.py` 都要求每次账户回答包含：

```text
summary
→ 业务 Section
→ conclusion
```

这与新规则冲突：

```text
simple  → summary + 业务 Section，不生成 conclusion
complex → summary + 业务 Section + conclusion
```

### 3.2 上游路由没有输出复杂度和最终卡片计划

当前流程为：

```text
账户意图识别
→ build_dispatch_plan.py 生成模块调用清单
→ 多个账户模块分别选择卡片
```

任务复杂度没有进入正式协议；卡片计划和参数识别分散在多个 reference 中。

### 3.3 固定编排没有真正代码化

当前 LLM 仍负责生成：

- 卡片完整结构；
- 业务 Section；
- Section 标题；
- 固定 narrative；
- Summary 和 Conclusion。

`compose_result.py` 主要负责事后校验，没有根据卡片计划主动生成确定性骨架。

### 3.4 简单与复杂任务共用同一个文案任务

重构前的 `mcp-summary-conclusion.md` 同时规划 Summary 和 Conclusion，没有区分：

- 简单事实回答；
- 复杂账户诊断。

### 3.5 当前测试验证的是旧协议

重构前已有 21 个单元测试，但包含“Conclusion 必须存在”等旧行为，需要迁移为新的复杂度协议测试。

## 4. 目标架构

```text
Global Route Extract
→ 场景分类和实体抽取保持不变
→ 原样透传 originalQuery

账户上游 LLM Planner
→ 识别账户意图及复杂程度
→ 选择卡片
→ 识别卡片业务参数
→ 输出账户计划

代码：生成固定骨架
→ 校验账户计划
→ 生成业务 Section
→ 生成卡片结构
→ 填入允许的卡片参数
→ 按固定业务顺序排序

根据 taskComplexity 调度
├── simple
│   → 选择最少必要 MCP
│   → 生成 Summary
│   → 不生成 Conclusion
│
└── complex
    → 选择完成当前诊断所需的 MCP
    → 执行组合诊断逻辑
    → 生成 Summary + Conclusion

代码：最终合并
→ 合并文字 Section 与业务骨架
→ 校验卡片和 Section
→ 补齐顶层字段
→ 输出 v2.2 JSON
```

## 5. 输入、内部计划与最终输出协议

三份协议必须分开管理，不能把内部调度字段写进上游输入或最终结果。

### 5.1 上游输入协议

账户域继续接收完整 Route Extract 结果，并由可信上游额外原样透传 `originalQuery`：

```json
{
  "originalQuery": "我今年收益怎么样",
  "scenes": [
    {
      "scene": "问账户",
      "weight": 0.95,
      "subQuery": "我今年收益怎么样"
    }
  ],
  "entities": {
    "fund_names": [],
    "fund_codes": [],
    "manager_names": [],
    "company_names": [],
    "market_subjects": [],
    "strategy_names": []
  },
  "primaryScene": "问账户",
  "isMultiScene": false,
  "orchestration": null,
  "clarify": {
    "needed": false,
    "question": null
  }
}
```

上游字段处理规则：

| 字段 | 是否保留 | 账户域用途 |
| --- | --- | --- |
| `originalQuery` | 保留，新增只读透传 | 保留完整语义、问题关系、指代和表达重点 |
| `scenes` | 完整保留 | 只处理其中 `scene = 问账户` 的记录 |
| `entities` | 完整保留六类数组 | 选卡、参数识别和 MCP 查询上下文 |
| `primaryScene` | 保留 | 表示全局主场景，不作为账户域是否执行的唯一条件 |
| `isMultiScene` | 保留 | 表示全局是否包含多条场景，不用于判断账户任务复杂度 |
| `orchestration` | 保留 | 上游预留字段，当前不由账户域解释或修改 |
| `clarify` | 保留 | 沿用上游结果，当前账户域不自行改写 |

账户域不得裁剪、重写或重新生成这份上游输入。处理过程中只读取所需字段，其余字段保持原样但不写入最终结果。

### 5.2 账户内部计划协议

账户 Planner 另行输出内部计划，不重复复制上游原始问题和全局字段：

```json
{
  "taskComplexity": "simple",
  "complexityReason": "用户只询问本年收益，不需要跨维度诊断",
  "primaryAccountIntent": "return_performance",
  "accountScenes": [
    {
      "intent": "return_performance",
      "weight": 0.95,
      "subQuery": "我今年收益怎么样"
    }
  ],
  "cardPlans": [
    {
      "cardId": "ACC-13-A",
      "params": {}
    }
  ]
}
```

约束：

- 账户 Planner 同时读取上游 `originalQuery` 和属于“问账户”的 `scenes`，但不得在内部计划中重写原始问题；
- `accountScenes[].subQuery` 用于单个账户意图的选卡和参数识别，不能替代上游 `originalQuery`；
- 原始问题包含其他业务域内容时，账户域只处理属于“问账户”的部分，不得回答其他业务域问题；
- `taskComplexity` 只允许 `simple` 或 `complex`；
- `complexityReason` 说明为什么需要或不需要跨维度诊断；
- `cardPlans` 只输出卡片编号和业务参数；
- LLM 不输出 `dataMode`、Section 类型、Section 标题或固定 narrative；
- 代码将 `params` 转换为最终卡片的 `data`；
- `taskComplexity` 属于内部调度信息，不写入最终 v2.2 JSON；
- 卡片选择和 MCP 选择继续保持独立。

### 5.3 最终输出协议

最终输出继续严格使用现有 v2.2 固定结构：

```json
{
  "version": "2.2",
  "meta": {
    "scene": "问账户",
    "intent": "return_performance"
  },
  "sections": [],
  "cards": [],
  "risk_warning": "投资有风险，请结合自身情况审慎决策。",
  "followUp": []
}
```

固定约束：

- 顶层只能包含 `version`、`meta`、`sections`、`cards`、`risk_warning`、`followUp`；
- `meta` 继续只包含现有的 `scene` 和 `intent`；
- 卡片继续只包含 `cardId`、`dataMode` 和 `data`；
- 不得加入 `originalQuery`、`taskComplexity`、`complexityReason`、`accountScenes`、`cardPlans`、MCP 原始数据或调试字段；
- 本次重构只根据复杂度决定 `sections[]` 中是否存在 `conclusion`，不改变其他顶层结构和卡片结构。

## 6. 目标文件结构

建议重构后的 `account-diagnosis` 为：

```text
account-diagnosis/
├── SKILL.md
├── agents/
│   └── openai.yaml
├── references/
│   ├── account-route-planner.md
│   ├── account-card-routing.md
│   ├── mcp-evidence.md
│   ├── simple-summary.md
│   ├── complex-diagnosis.md
│   └── result-composer.md
├── scripts/
│   ├── account_contract.py
│   ├── build_result_skeleton.py
│   └── compose_result.py
└── tests/
    ├── test_account_pipeline.py
    ├── test_build_result_skeleton.py
    └── test_compose_result.py
```

说明：

- `SKILL.md` 只保留入口协议、工作流、条件调度和失败处理；
- `account-route-planner.md` 定义上游 LLM 输出协议和复杂度判断；
- `account-card-routing.md` 集中维护卡片选择和参数识别规则；
- `mcp-evidence.md` 维护公共 MCP 能力、数据质量和证据边界；
- `simple-summary.md` 只负责简单任务；
- `complex-diagnosis.md` 负责复杂账户诊断；
- `build_result_skeleton.py` 将卡片计划转换为固定业务骨架；
- `compose_result.py` 根据复杂度合并并校验最终结果。

旧 reference 和脚本在新流程验证通过后删除，避免重构过程中出现不可运行的中间状态。

## 7. 分阶段实施

### 阶段一：锁定文档和协议基线

1. 确认当前五份项目 Markdown 为重构依据；
2. 单独保存 Markdown 变更，不包含原始 PDF；
3. 固化上游输入协议，明确 `originalQuery` 和现有 Route Extract 字段的保留方式；
4. 固化账户内部计划 JSON Schema；
5. 再次确认最终 v2.2 输出和卡片结构不变；
6. 明确 simple/complex、账户诊断类/自选基金类的边界。

验收：所有后续代码都能追溯到明确的文档规则。

### 阶段二：建立账户 Planner

1. 将账户意图、复杂度、卡片选择和参数识别合并为一个上游 LLM 任务；
2. 同时读取上游不可改写的 `originalQuery` 和 `scenes` 中的问账户记录；
3. 输出统一账户计划；
4. 增加计划校验，但不要求 Planner 重复输出 `originalQuery`；
5. 不允许下游代码重新解释用户语义。

验收：同一用户问题只产生一份确定的复杂度结果和卡片计划。

### 阶段三：代码生成固定业务骨架

实现 `build_result_skeleton.py`：

- 校验合法卡片编号；
- 校验卡片参数白名单；
- 拒绝身份参数；
- 添加 `dataMode: deferred`；
- 将 `params` 平铺到 `data`；
- 根据 cardId 生成业务 Section 类型、标题和固定 narrative；
- 按固定业务顺序排序；
- 拒绝重复卡片；
- 阻止账户诊断类和自选基金类混排。

验收：给定同一个账户计划，代码始终生成完全一致的业务骨架。

### 阶段四：拆分简单与复杂大模型任务

简单任务：

```text
用户问题 + 账户计划
→ 选择最少必要 MCP
→ 生成一个 Summary
→ 不生成 Conclusion
```

复杂任务：

```text
确定账户范围
→ 从单品转换为组合结构
→ 评价收益、超额收益和回撤
→ 定位主要贡献和拖累
→ 判断结构是否放大贡献或拖累
→ 确定问题优先级
→ 生成 Summary + Conclusion
```

验收：简单任务不能输出账户级诊断；复杂任务必须形成跨维度关系和优先级。

### 阶段五：改造最终编排

修改 `compose_result.py`：

```text
simple
→ 必须有一个 summary
→ conclusion 必须不存在

complex
→ 必须有一个 summary
→ 必须有一个 conclusion
```

继续保留：

- v2.2 六个顶层字段；
- 18 张合法账户卡片；
- 卡片参数白名单；
- Section 固定顺序；
- 卡片和 Section 一一关联；
- 身份参数隔离；
- followUp 去重和数量限制；
- 风险提示注入。

验收：最终 JSON 不包含内部复杂度、MCP 原始数据、身份信息或调试字段。

### 阶段六：更新 Skill 和清理旧实现

1. 精简 `SKILL.md`；
2. 更新 `agents/openai.yaml`；
3. 删除已被新 Planner 和新 references 替代的旧文件；
4. 确认 Skill 不依赖目录外文件；
5. 运行 Skill 结构校验。

验收：Skill 入口简洁，references 按需加载，没有同一规则在多处重复维护。

## 8. 测试矩阵

| 用户问题 | 复杂度 | 预期卡片 | Conclusion |
| --- | --- | --- | --- |
| “我今年收益怎么样” | simple | ACC-13-A | 无 |
| “我都买了什么，今年赚了多少” | simple | ACC-11、ACC-13-A | 无 |
| “我的资产怎么分布” | simple | ACC-12 | 无 |
| “我的自选基金今天怎么样” | simple | ACC-18 | 无 |
| “我的账户怎么样” | complex | 完整诊断相关卡片 | 有 |
| “哪些重仓产品是主要拖累” | complex | ACC-11、ACC-15 | 有 |
| “持仓结构为什么导致收益不好” | complex | 结构、收益、归因相关卡片 | 有 |

还需覆盖：

- 单一问题和复合问题的 `originalQuery` 均被逐字保留；
- `subQuery` 拆分后仍能通过 `originalQuery` 保留“整体判断”“为什么”等关系语义；
- 原始问题包含其他业务域时，账户域不越界回答；
- 单张卡片也可以是复杂任务；
- 多张卡片也可以是简单任务；
- ACC-15 `dateType` 合法、缺失和非法值；
- ACC-19、ACC-03/05/06/08/10 的可选参数；
- 重复卡片和错误 Section 映射；
- 账户诊断类与自选基金类混排；
- 简单任务错误携带 Conclusion；
- 复杂任务缺少 Conclusion；
- MCP 全部成功、部分成功、空数据和失败；
- deferred 卡片在 MCP 失败时仍正常输出；
- 最终结果不包含身份和 MCP 原始数据。

## 9. 验收标准

重构完成必须满足：

1. 简单任务恰好有一个 `summary`，没有 `conclusion`；
2. 复杂任务恰好有一个 `summary` 和一个 `conclusion`；
3. 原始用户问题只存在于上游输入上下文，通过 `originalQuery` 原样透传，不由 LLM 重建或写入最终结果；
4. 上游 LLM 输出任务复杂度、卡片编号和卡片业务参数；
5. 卡片结构、业务 Section、顺序和固定字段全部由代码生成；
6. LLM 不能修改现有卡片结构；
7. 卡片计划和 MCP 调用计划相互独立；
8. 复杂诊断能够建立结构、表现和归因之间的关系，并确定优先级；
9. 没有 KYC 时不生成适配性判断或调仓建议；
10. v2.2 六个顶层字段、`meta` 结构、卡片结构和现有卡片编号保持不变；
11. 所有单元测试和场景测试通过；
12. `account-diagnosis` 保持独立、自包含；
13. 原始 PDF 不纳入本次重构提交。
