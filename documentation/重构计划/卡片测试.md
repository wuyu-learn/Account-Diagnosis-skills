# 卡片测试设计

## 背景

账户域正常链路中，"意图识别 → 选卡"由 Planner（LLM）完成，结果受模型判断影响，不可完全复现。测试和验收卡片编排时，需要一条**确定性路径**：给定固定输入，产出固定卡片计划，绕过 Planner 的语义判断。

参考其他模块的卡片测试机制（输入 `000001卡片测试` → 全量输出；输入 `000001,002910 frt06测试` → 单卡多标的对比），账户域设计自己的测试模式，卡片编号使用账户域现有 `ACC-XX`。

## 测试模式设计推演

### 触发

上游输入的 `originalQuery` / `subQuery` 中带有 `问账户：` 前缀的测试指令：

- `问账户：全部卡片测试` → **全量模式**：一次输出所有账户卡片（已确认）
- 单卡模式指令格式待定（候选：`问账户：ACC-15测试`）

`meta.intent` 协议不变，仍使用账户意图值；测试信号只来自输入内容中的 `问账户：` 关键词。

### 拦截位置

在 `normalize_input.py` 之后、Planner 之前做**确定性代码拦截**（不经过 LLM）：

```text
normalize_input.py
→ 检测 originalQuery/subQuery 是否匹配测试指令
    ├── 是 → 直接生成固定的账户计划（cardPlans 按规则展开），跳过 Planner
    └── 否 → 正常走 Planner
```

这符合项目"代码负责调度与校验"的原则，测试结果可复现。

### 拦截后生成什么

测试模式本质是绕过"意图识别 → 选卡"的不确定性，用确定性代码直接产出固定 `cardPlans`。测试计划唯一与共享脚本冲突的地方是**诊断类与自选类混排**（ACC-18 与诊断类同出），其余形态（ACC-19 单卡空参、参数字符串、title/narrative 逐字匹配）均与 `CARD_SPECS` 一致。因此测试模式**自带一条隔离链路**（`scripts/test_mode/`），仅对混排规则破例，骨架生成、回填、合并、校验在测试模式自己的脚本里做，**共享脚本一行不改**：

```text
测试指令
→ 确定性拦截器生成账户计划（taskComplexity / cardPlans）
→ scripts/test_mode/build_test_skeleton.py（测试模式自有，仅放开混排，其余按共享规则校验 + 出骨架）
→ 文案与 MCP 步骤（queryHoldingDetail 取大类结构 + queryShareDetail 取份额 serialNo + 固定 Summary）
→ scripts/test_mode/enrich_test_cards.py（注入 ACC-19 单值 productId / serialNo·uri）
→ scripts/test_mode/compose_test_result.py → v2.2 JSON（测试模式自有，仅放开混排校验）
```

## 全量模式实现逻辑

触发指令：`问账户：全部卡片测试`。

已确认规则：

- **卡片集**：全部 18 张账户卡片（ACC-01~15 含 13-A/13-B 共 17 张诊断类 + ACC-18 自选基金卡），测试模式对"诊断类与自选类不混排"限制破例；
- **复杂度**：默认走简单路径（`taskComplexity = simple`），只生成 Summary，不生成 Conclusion。

### 处理流程

```text
上游输入
→ normalize_input.py（适配为标准 Route Extract，现有逻辑不变）
→ scripts/test_mode/interceptor.py（新增，确定性代码）
    检测 originalQuery / 问账户 subQuery 是否匹配 "问账户：全部卡片测试"
    ├── 匹配 → 直接生成固定账户计划，跳过 Planner
    └── 不匹配 → 正常走 Planner（共享链路，不受测试模式影响）
→ scripts/test_mode/build_test_skeleton.py（测试模式自有，不经过 build_result_skeleton.py）
    → 按测试模式规则校验并生成 businessItems（ACC-19 单卡空参、允许混排）
→ LLM 任务：queryHoldingDetail（type=1，取 5 大类结构）+ queryShareDetail（不传业务参，取份额 serialNo/uri），并生成固定 Summary
→ scripts/test_mode/enrich_test_cards.py（测试模式自有，不经过 enrich_share_identifiers.py）
    → ACC-19：挑一个同 productId（fundId）下 serialNo 数 ≥ 2 的多渠道产品，注入单值 productId（字符串）
    → ACC-03/05/06/08/10：按各自大类挑一笔份额，注入 serialNo/uri（来源 queryShareDetail）
→ scripts/test_mode/compose_test_result.py → v2.2 JSON（测试模式自有，不经过 compose_result.py）
```

> **MCP 调用参数口径**：两个接口都**必须透传上游注入的 `sso_cookie`** 作为请求参数，`custNo` 不解析、由 MCP 侧从 `sso_cookie` 自取。业务参数：`queryShareDetail` 免参（`productId` 可选，不传返全部）；`queryHoldingDetail` 必传 `type=1`（按资产五大类汇总）。`custNo`/`accountName` 等身份参数不传，身份注入属上游可信运行时职责，不在 skill 范围。

参数取值依据：

- **ACC-15**（已确认）：`dateType` 是必填参数（`account_contract.py` 中 `requiredParams`），测试模式无用户时间表达，按协议默认值取 `N`（今日）；
- **ACC-19**（全量测试模式只出一张，空参占位）：拦截器 `params` 保持 `{}`，与份额级卡片同一套占位逻辑；`productId` 在 `queryShareDetail` 取数后由 `enrich_test_cards.py` 回填。回填策略：优先挑**同一 `fundId` 下 serialNo 数 ≥ 2** 的多渠道产品，将 `fundId` 作为**单值字符串**注入 `data.productId`；没有多渠道产品时退而挑任一产品；完全没有产品时卡片保留、`productId` 不填（与份额级「未命中保留不填」一致）；
- **ACC-03/05/06/08/10**（份额级，见「份额级卡片的取值」）：拦截器阶段 `params` 保持 `{}`（目标份额依赖 MCP 数据，拦截器拿不到）；`serialNo`/`uri` 由 `queryShareDetail` 取数后回填——按各自大类（大类归属来自 `queryHoldingDetail`）挑一笔份额注入；
- `accountScenes` 必须声明全部 5 个意图，否则测试模式骨架脚本（`build_test_skeleton.py`）的"卡片类型 ⊆ 已声明意图"校验不通过。

### ACC-19 的产品 ID 回填（全量测试模式）

全量测试模式下 ACC-19 只出**一张空参卡**，由 `enrich_test_cards.py` 在 `queryShareDetail` 取数后回填一个真实的 `productId`（`fundId`），让前端能调用 `/share-detail` 接口取到多份额明细。

判定口径：**多渠道产品** = 同一 `fundId` 下 `serialNo` 数 ≥ 2（每个 `serialNo` 对应一个渠道）。

取数逻辑：

```text
queryShareDetail → itemList → 按 fundId 聚合 serialNo
                            → serialNo 数 ≥ 2 的 fundId = 多渠道产品
                              （优先）任选一个多渠道 fundId 注入 data.productId
                              （无多渠道）任选一个 fundId 注入 data.productId
                              （完全无份额）卡片保留、productId 不填
```

- `productId`（即接口字段 `fundId`）是**单值字符串**，与常规链路 `account_contract.py` 对 ACC-19 的契约一致；
- 注入字段为 `data.productId`，不是 `params.productId`；
- 某账户完全没有份额时，卡片保留、`data.productId` 不填，与份额级卡片「未命中保留不填」一致。

时序与「MCP 数据不入卡」原则的关系：

- 拦截器在 Planner 之前运行，拿不到 MCP 数据，因此 ACC-19 与份额级卡片一样**先以空参占位**（`params: {}`），保证拦截器确定性；
- `productId` 在 `queryShareDetail` 取数后由测试模式回填脚本（`enrich_test_cards.py`）注入，回填思路沿用 `enrich_share_identifiers.py`。

示例（产品 A 同 fundId 下有两个 serialNo，产品 B 只有一个）：

```json
[
  { "cardId": "ACC-19", "params": {} }
]
```

回填后：

```json
[
  { "cardId": "ACC-19", "data": { "productId": "A" } }
]
```

### 份额级卡片的取值（ACC-03/05/06/08/10）

份额级卡片要取的是**一笔具体份额的 `serialNo`/`uri`**（定位标识，非分析数据），让每张都渲染出真实数据。

关键：能稳定给 `serialNo`/`uri` 的是 **`queryShareDetail`**（份额级、每笔带 `serialNo`+`uri`）；`queryHoldingDetail` 是分类汇总、`serialNo` 在"产品无子项时可空"，不能拿它喂份额级卡片。但 `queryShareDetail` **不带 `productType`**，所以要按大类挑份额，大类归属得从 `queryHoldingDetail` 来。两个接口配合：

```text
queryHoldingDetail(type=1) → 卡片所属大类(categoryCode)下的 fundId 集合
queryShareDetail            → itemList 里这些 fundId 的 serialNo/uri
→ 随机挑一笔 → 注入该卡 data.serialNo / data.uri
```

| 卡片 | 大类（categoryCode） |
| --- | --- |
| ACC-03 | `1`（公募基金） |
| ACC-05、ACC-06 | `6`（投顾） |
| ACC-08 | `0`（货币） |
| ACC-10 | `4`（资管/专户） |

（份额级卡片是固定 cardId，覆盖公募基金/投顾/货币/资管四大类；"组合"(`3`)大类由 ACC-19 覆盖，无对应份额级 cardId。）

- `serialNo`/`uri` 来源是 `queryShareDetail`（不是 `queryHoldingDetail`）；大类归属是 `queryHoldingDetail`（`queryShareDetail` 不带 `productType`）；
- 时序与 ACC-19 一致：拦截器阶段 `params` 为 `{}`（目标份额要 MCP 后才知道），`serialNo`/`uri` 在取数后由测试模式回填脚本（`enrich_test_cards.py`）注入，思路沿用 `enrich_share_identifiers.py`；
- 某大类无份额时，卡片保留、`serialNo`/`uri` 不填（与「未命中份额时卡片保留、data 不填」一致）。

### 与共享链路的关系：不经过、不修改

测试模式的放宽形态会被共享脚本挡住，所以**测试模式自带校验和编排，根本不经过共享脚本**，不存在"在共享脚本里加开关放开"的改动：

| 共享脚本 | 拦截测试计划的点 | 测试模式的处理 |
| --- | --- | --- |
| `build_result_skeleton.py` | 同 cardId 不重复、参数必须字符串、`CARD_SPECS` 允许参数、不混排 | 改走 `build_test_skeleton.py`，仅对「诊断/自选混排」破例，其余按共享规则校验 |
| `compose_result.py` | 重新按 `CARD_SPECS` 校验 cardId/参数/title/narrative、不重复、不混排 | 改走 `compose_test_result.py`，仅对「诊断/自选混排」破例 |
| `account_contract.py` | `CARD_SPECS["ACC-19"]` 只允许单值 `productId` | 测试模式直接沿用共享 `CARD_SPECS["ACC-19"]`，不再自建 ACC-19 规格 |

测试模式自带的放宽规则（只在 `scripts/test_mode/` 内生效，正常路径与 `references/` 不受影响）：

- **诊断/自选混排**：允许 ACC-18 与诊断类同出；
- 其余约束（卡片编号合法、同 cardId 不重复、参数必须字符串、`CARD_SPECS` 允许参数、意图覆盖、primary 有卡、section 顺序、ACC-15 dateType、title/narrative 逐字匹配）保持启用。

### 输出结构

→ holding_structure × 2（ACC-11、ACC-12）
