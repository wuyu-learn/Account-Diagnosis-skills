# AI 顾问账户路由

## 文档定位

本文档承接 [`AI顾问整体架构.md`](./AI顾问整体架构.md) 中 Global Phase B 的“问账户”分支，说明进入 `account-diagnosis` 后的账户域内部路由：账户意图和任务复杂度如何识别、卡片和参数如何确定、代码如何完成确定性拼接，以及简单 Summary 任务和复杂账户诊断任务如何调度。

两份文档的边界是：整体架构回答“账户域处于全局流程的什么位置、与其他阶段如何衔接”，本文档回答“进入账户域后如何路由和调度”。本文档不重复定义全局 Phase、卡片结构、MCP 接口或最终 v2.2 响应字段。回复结构和组件编排见 [`AI顾问结果输出与组件编排.md`](./AI顾问结果输出与组件编排.md)，卡片及数据规则见 [`AI顾问账户卡片与数据.md`](./AI顾问账户卡片与数据.md)。

## 上游输入边界

账户域接收 Global Phase A 的完整 Route Extract JSON：保留新增的只读 `originalQuery`，以及现有的 `scenes`、`entities`、`primaryScene`、`isMultiScene`、`orchestration` 和 `clarify`。不增加包装层，也不删改现有字段。

- `originalQuery` 保留用户问题的完整语义，账户域只能读取，不能改写；
- `scenes[].subQuery` 用于拆分账户意图、选卡和识别参数，不能替代 `originalQuery`；
- 账户域只处理 `scene = 问账户` 的记录，但接收的仍是完整上游 JSON；
- 上游字段和账户内部计划字段都不写入最终 v2.2 结果。

## 账户域内部调度

```text
上游大模型路由
→ 识别用户意图及复杂程度
→ 判断使用哪些卡片
→ 识别卡片需要携带的参数
→ 输出卡片计划和复杂度结果

代码
→ 按现有卡片定义完成确定性拼接
→ 生成卡片结构、业务 Section、顺序和固定字段

根据上游识别的意图复杂度进行调度
├── 简单任务
│   → 调用简单 Summary 大模型任务
│   → 使用最少必要的 MCP，直接回答单一问题
│   → 不生成 Conclusion
│
└── 复杂任务
    → 调用复杂账户诊断大模型任务
    → 综合结构、收益、回撤和归因等证据
    → 生成诊断型 Summary/Conclusion

代码
→ 合并并校验最终结果
```

## 任务复杂度

### 判定对象

简单或复杂描述的是：**生成本次回答所需的理解与诊断深度，并决定是否需要 `conclusion`**。

它不改变卡片结构，也不决定卡片由谁拼接。无论简单还是复杂，卡片计划都由上游大模型生成，卡片结构、业务 Section、顺序和固定字段都先由代码按照现有协议拼接。

复杂度不能按以下表面特征直接判断：

- 不能按用户问题的字数判断；
- 不能按选中卡片的数量判断；
- 不能按 MCP 调用数量机械判断；
- 不能因为问题中出现“怎么样”就直接判为复杂，必须看“怎么样”修饰的是单一对象还是整个账户。

例如：

```text
“我今年收益怎么样”
→ 对象和指标范围明确，只回答收益表现，属于简单任务。

“我的账户怎么样”
→ 没有限定单一指标，期望得到整体账户评价，属于复杂任务。
```

### 简单任务

简单任务是：**用户提出了明确、有限、可以直接回答的账户事实问题，使用 `summary` 即可完成回答，不需要额外生成 `conclusion`。**

通常同时满足以下条件：

1. 查询对象明确，例如全账户、基金账户、投顾账户、指定产品或自选基金；
2. 回答目标明确，例如金额、持仓、份额、收益、收益日历或归因结果；
3. 时间范围、产品范围等必要参数可以从用户表达中识别，或允许使用已有协议默认值；
4. 每个子问题可以独立回答，不需要解释多个维度之间的关系；
5. 使用最少必要的 MCP 即可取得直接答案；
6. `summary` 能够完整承载本次直接答案，不需要账户级收束。

#### 示例

| 用户问题 | 判为简单任务的原因 |
| --- | --- |
| “我的账户有多少钱” | 只查询账户规模和构成 |
| “我的基金账户怎么样” | 对象限定为基金账户，只回答直接概况 |
| “我持有这只基金多少份” | 对象和指标均明确 |
| “我都买了哪些产品” | 只查询持仓列表 |
| “我的资产怎么分布” | 只查询结构分布事实 |
| “我今年收益怎么样” | 时间范围和收益指标明确 |
| “看一下历年收益” | 只查询自然年度收益结果 |
| “哪个月亏得最多” | 只查询收益日历中的时间明细 |
| “哪些产品拖累了收益” | 只查询已有归因结果中的拖累项 |
| “我的自选基金今天涨跌如何” | 对象和时间范围明确 |

具体卡片编号由上游根据用户意图选择，映射规则见 [`AI顾问结果输出与组件编排.md`](./AI顾问结果输出与组件编排.md) 和 [`AI顾问账户卡片与数据.md`](./AI顾问账户卡片与数据.md)，本文档不重复维护卡片清单。

多个简单问题同时出现，不自动升级为复杂任务。例如：

```text
“我都买了哪些产品，今年赚了多少”
```

虽然会命中持仓结构和收益表现两类卡片，但两个问题可以分别取得事实后直接汇总，不要求解释持仓与收益之间的关系，因此仍可以调用简单 Summary 任务。

#### 输出结构

```text
summary = 查询范围 + 1～3 个关键事实 + 对用户问题的直接回答
```

简单任务的结果结构为：

```text
summary
→ 实际命中的业务 Section 和卡片
```

简单任务不生成 `conclusion` Section，也不得把局部结果扩展成“账户整体健康”“配置合理”或“风险可控”等完整诊断结论。需要继续查看的方向可以放入 `followUp`，不需要为此增加 `conclusion`。

### 复杂任务

复杂任务是：**用户希望得到整个账户的综合评价，或者要求建立多个账户维度之间的关系，`summary` 和 `conclusion` 必须经过诊断、归纳和优先级判断才能回答。**

满足以下任一条件即可判为复杂任务：

1. 用户提出开放式整体问题，例如“我的账户怎么样”“帮我看看账户有什么问题”；
2. 用户明确要求“账户诊断”“全面分析”“账户体检”或“整体评价”；
3. 用户要求综合账户规模、产品持仓、资产结构、收益、超额收益、回撤或收益归因中的多个维度；
4. 用户要求解释维度之间的关系，例如“持仓结构为什么导致收益不好”；
5. 用户要求从多个发现中确定主要问题、主要贡献、主要拖累或关注优先级；
6. 用户的问题不能通过并列陈述若干事实完成，必须形成一个账户级综合判断。

#### 示例

| 用户问题 | 复杂原因 | 诊断重点 |
| --- | --- | --- |
| “我的账户怎么样” | 答案范围开放，期望整体评价 | 结构、收益、风险和归因的综合诊断 |
| “给我的账户做一次全面体检” | 明确要求完整诊断 | 账户总览、持仓结构、收益表现和收益归因 |
| “我的账户主要有什么问题” | 需要比较多个发现并确定优先级 | 找出最重要的结构或表现问题 |
| “持仓结构为什么导致收益不好” | 要求建立结构与收益之间的关系 | 持仓、资产结构、收益和归因的交叉判断 |
| “整体看我的收益和风险是否匹配” | 需要综合收益、超额收益和回撤 | 收益质量与回撤表现的联合评价 |
| “哪些重仓产品是账户的主要拖累” | 需要关联持仓权重和产品归因 | 持仓明细与归因结果的交叉分析 |

对于“我的账户怎么样”这类完整账户诊断，路由层只确定进入复杂账户诊断任务，不在此展开诊断推理。复杂任务如何从 MCP 证据形成核心发现、`summary` 和 `conclusion`，见 [`AI顾问复杂账户诊断输出.md`](./AI顾问复杂账户诊断输出.md)；最终 Section 和卡片编排以 [`AI顾问结果输出与组件编排.md`](./AI顾问结果输出与组件编排.md) 为准。

路由层要求复杂任务的外层结构为：

```text
summary
→ 实际命中的业务 Section 和卡片
→ conclusion
```

复杂任务仍应按实际诊断问题规划 MCP，不表示无条件调用全部 MCP。卡片计划和 MCP 计划继续保持独立：卡片决定前端展示内容，MCP 只为 `summary` 和 `conclusion` 提供本次需要的真实证据。

#### 输出结构

```text
summary = 诊断范围 + 最重要的账户事实 + 当前核心发现

conclusion = 跨维度综合判断 + 主要关注点及优先级 + 数据边界或后续方向
```

复杂任务只能使用本次 MCP 实际返回且校验通过的证据。数据不足时应降级为局部诊断，明确哪些维度暂时无法判断，不能用 deferred 卡片尚未加载的数据补足结论。

### 判定顺序

上游大模型按以下顺序判断：

```text
第一步：用户是否明确要求整体账户诊断、体检或主要问题判断？
├── 是 → 复杂任务
└── 否
    ↓
第二步：回答是否需要建立两个或以上诊断维度之间的关系？
├── 是 → 复杂任务
└── 否
    ↓
第三步：多个子问题是否都可以作为独立事实问题直接回答？
├── 是 → 简单任务
└── 否 → 复杂任务
```

补充规则：

- 单张卡片也可能对应复杂任务，例如开放式的“我的账户怎么样”；
- 多张卡片也可能只是多个简单问题的并列展示；
- MCP 失败、空数据或部分可用只影响输出降级，不改变原始任务复杂度；
- 自选基金估值属于独立回答大类，不与账户诊断类卡片混排；
- 跨业务大类问题继续遵守 `primaryAccountIntent` 和现有混排限制，复杂度判断不改变这些协议。

## 上游复杂度输出

复杂度结果属于内部路由信息，不写入卡片结构。建议上游卡片计划同时提供：

```json
{
  "taskComplexity": "simple",
  "complexityReason": "用户询问明确的本年收益结果，不需要跨维度诊断",
  "cards": []
}
```

`taskComplexity` 只允许：

```text
simple
complex
```

代码不重新解释用户语义，只根据该结果调度简单 Summary 任务或复杂账户诊断任务。

## 职责边界

- 上游大模型输出任务复杂度、卡片计划和卡片业务参数。
- 代码消费上游结果完成确定性拼接，不重新判断卡片或解析参数。
- 简单任务调用简单 Summary 大模型任务，不生成 `conclusion`。
- 复杂任务调用复杂账户诊断大模型任务，生成诊断型 Summary/Conclusion。
- Summary 和复杂任务的 Conclusion 只能使用本次 MCP 实际返回且校验通过的数据，不得推断 deferred 卡片尚未加载的内容。
- 最终结果由代码统一合并和校验。
- 本文档不改变卡片结构、卡片编号、MCP 能力或 v2.2 顶层字段定义。

## 结果结构约束

账户任务的结果结构按上游输出的 `taskComplexity` 执行：

```text
simple  → 必须有一个 summary，不能有 conclusion
complex → 必须有一个 summary 和一个 conclusion
```

该规则只影响 Section 编排和校验，不改变任何卡片结构定义。本文档及相关 `documentation` 文档已按此规则统一；`account-diagnosis` Skill、脚本和测试尚未修改，本阶段不处理代码实现。
