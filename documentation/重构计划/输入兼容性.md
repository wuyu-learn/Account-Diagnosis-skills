# 输入兼容性设计

## 背景

`account-diagnosis` 在 `SKILL.md` 和 `references/account-route-planner.md` 中定义了严格的上游输入协议，要求必须包含：

```json
{
  "originalQuery": "...",
  "scenes": [...],
  "entities": {
    "fund_names": [],
    "fund_codes": [],
    "manager_names": [],
    "company_names": [],
    "market_subjects": [],
    "strategy_names": []
  },
  "primaryScene": "问账户",
  "isMultiScene": false,
  "orchestration": null,
  "clarify": {...}
}
```

但实际运行中，上游 Agent 传入的输入并不总是严格符合该协议。例如：

- 缺少 `originalQuery`；
- `entities` 使用 `funds` 对象数组而非 `fund_names`/`fund_codes` 字符串数组；
- 整个输入是一段自然语言文本，不是 JSON。

当前实现缺少输入适配层，导致这些输入会被直接判定为结构错误。本设计旨在增加一个轻量输入适配层，让 `account-diagnosis` 对上游更宽容，同时不破坏内部协议的确定性。

## 目标

1. **兼容非严格 JSON 输入**：从文本、缺字段 JSON 或变体 JSON 中提取足够信息；
2. **不破坏内部协议**：适配后仍输出标准 `account-plan` 给 `build_result_skeleton.py`；
3. **最小化上游改动**：允许上游逐步迁移，不需要一次性切换到严格协议；
4. **可测试、可回退**：适配行为有明确规则，错误场景返回结构错误并说明原因。

## 当前输入链分析

```text
上游 Agent
  → 原始输入（可能为 JSON / 类 JSON / 自然语言）
  → account-diagnosis 入口
  → references/account-route-planner.md（LLM 任务）
  → 账户计划 JSON
  → scripts/build_result_skeleton.py
  → scripts/compose_result.py
  → v2.2 JSON
```

当前入口没有显式适配步骤， Planner 直接读取上游输入。这导致 Planner 需要同时承担"解析输入"和"生成计划"两个职责，增加了不确定性。

## 适配层位置

建议新增 `scripts/normalize_input.py`，放在账户 Planner 之前：

```text
上游输入
  → scripts/normalize_input.py
  → 标准 Route Extract JSON
  → Planner（account-route-planner.md）
  → build_result_skeleton.py
  → compose_result.py
```

适配层只负责"把各种输入形态转成标准上游输入"，不做账户意图识别、不做卡片选择、不调用 MCP。

## 需要兼容的输入形态

### 形态一：严格协议 JSON

已经是标准格式，直接透传。

### 形态二：缺少 `originalQuery`

尝试从以下位置补齐：

1. `scenes[0].subQuery`（如果存在且非空）；
2. `scenes` 中所有问账户 `subQuery` 用空格拼接；
3. 如果仍无法得到，返回结构错误。

规则：

- `originalQuery` 只用于保留完整语义，不用于替换 `subQuery`；
- 补齐的 `originalQuery` 需要标注为"派生"，但内部协议不区分来源。

### 形态三：`entities` 结构变体

当前文档协议要求六类字符串数组，实际变体可能包括：

- `funds` 数组：`[{ "name": "...", "code": "..." }]` → 转换为 `fund_names` 和 `fund_codes`；
- `fund` 单对象：提取 `name`/`code`；
- `manager`、`company` 单字符串或数组：转换为 `manager_names`、`company_names`；
- 缺少某些字段：补空数组；
- 未知字段：保留但不使用。

### 形态四：非 JSON 文本

当输入不是有效 JSON 时，使用轻量规则或小型 LLM 任务提取：

```json
{
  "originalQuery": "<原始文本>",
  "scenes": [{ "scene": "问账户", "weight": 1.0, "subQuery": "<原始文本>" }],
  "entities": { "fund_names": [], "fund_codes": [], "manager_names": [], "company_names": [], "market_subjects": [], "strategy_names": [] },
  "primaryScene": "问账户",
  "isMultiScene": false,
  "orchestration": null,
  "clarify": { "needed": false, "question": null }
}
```

也就是说，无法解析时把整个文本当作原始问题和唯一子问题，entities 留空，交给下游 Planner 处理。

### 形态五：部分字段存在

例如只有 `scenes` 没有 `entities`、只有 `originalQuery` 没有 `scenes` 等，按照以下优先级补齐：

| 缺失字段 | 补齐来源 | 无法补齐时的行为 |
| --- | --- | --- |
| `originalQuery` | `scenes[].subQuery` 拼接 | 结构错误 |
| `scenes` | 从 `originalQuery` 生成一条默认问账户 scene | 透传给 Planner |
| `entities` | 空对象 | 透传空对象 |
| `primaryScene` | 若存在问账户 scene 则为"问账户" | 保留原值或设为 null |
| `isMultiScene` | 根据 `scenes` 数量判断 | 设为 false |
| `clarify` | 默认 `{ "needed": false, "question": null }` | 透传默认值 |

## 适配层输出协议

`normalize_input.py` 输出严格符合当前 `SKILL.md` 上游输入协议的 JSON：

```json
{
  "originalQuery": "...",
  "scenes": [...],
  "entities": {
    "fund_names": [],
    "fund_codes": [],
    "manager_names": [],
    "company_names": [],
    "market_subjects": [],
    "strategy_names": []
  },
  "primaryScene": "问账户",
  "isMultiScene": false,
  "orchestration": null,
  "clarify": { "needed": false, "question": null }
}
```

适配层不输出 `taskComplexity`、`cardPlans` 等内部字段。

## 对 Planner 的影响

引入适配层后，Planner 可以假设输入已经符合标准协议，继续按现有规则执行。但建议在 `account-route-planner.md` 中增加一句：

> 上游输入已由 `normalize_input.py` 适配为标准 Route Extract。Planner 按标准协议读取，不再处理变体结构。

这样职责清晰：适配层负责输入兼容，Planner 负责意图和复杂度判断。

- `account-diagnosis/tests/test_account_pipeline.py`：增加从非标准输入到最终输出的端到端用例。

### `normalize_input.py` 核心逻辑草稿

```python
def normalize_input(raw: Any) -> dict[str, Any]:
    # 1. 如果是字符串，尝试按 JSON 解析
    # 2. 如果是 dict，进入字段适配
    # 3. 补齐 originalQuery、scenes、entities、primaryScene 等
    # 4. 转换 entities 变体为标准六类数组
    # 5. 返回标准 Route Extract JSON
```

### 边界行为

- 输入为空字符串或 None → 结构错误；
- JSON 解析失败 → 降级为自然语言处理；
- 有 `scenes` 但无任何"问账户" scene → 结构错误；
- `originalQuery` 和 `scenes` 都缺失 → 结构错误；
- entities 中存在无法识别的字段 → 保留但忽略。

## 测试建议

| 用例 | 输入 | 期望 |
| --- | --- | --- |
| 严格协议 | 标准 Route Extract | 原样输出 |
| 缺少 originalQuery | 只有 scenes 和 entities | 从 scenes 派生 originalQuery |
| entities 变体 | `funds` 对象数组 | 转换为 fund_names / fund_codes |
| 自然语言文本 | "我今年收益怎么样" | 生成默认 scenes 和 entities |
| 空输入 | "" | 结构错误 |
| 无问账户 scene | scenes 里全是其他业务域 | 结构错误 |
| 部分字段 | 只有 originalQuery | 生成默认 scenes |
