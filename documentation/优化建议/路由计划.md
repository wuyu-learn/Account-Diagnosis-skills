# 路由计划

## Account Diagnosis 内部调度顺序

```text
上游大模型路由
→ 识别用户意图及复杂程度
→ 判断使用哪些卡片
→ 识别卡片需要携带的参数
→ 输出卡片计划和复杂度结果

代码
→ 按现有卡片定义完成确定性拼接
→ 生成卡片结构、业务 Section、顺序和固定字段

根据上游识别的意图复杂度进行调度
├── 简单任务
│   → 调用简单 Summary 大模型任务
│   → 使用最少必要的 MCP，直接回答单一问题
│   → 不生成 Conclusion
│
└── 复杂任务
    → 调用复杂账户诊断大模型任务
    → 综合结构、收益、回撤和归因等证据
    → 生成诊断型 Summary/Conclusion

代码
→ 合并并校验最终结果
```

## 简单任务与复杂任务的定义

### 1. 判定对象

简单或复杂描述的是：**生成本次回答所需的理解与诊断深度，并决定是否需要 `conclusion`**。

它不改变卡片结构，也不决定卡片由谁拼接。无论简单还是复杂，卡片计划都由上游大模型生成，卡片结构、业务 Section、顺序和固定字段都先由代码按照现有协议拼接。

复杂度不能按以下表面特征直接判断：

- 不能按用户问题的字数判断；
- 不能按选中卡片的数量判断；
- 不能按 MCP 调用数量机械判断；
- 不能因为问题中出现“怎么样”就直接判为复杂，必须看“怎么样”修饰的是单一对象还是整个账户。

例如：

```text
“我今年收益怎么样”
→ 对象和指标范围明确，只回答收益表现，属于简单任务。

“我的账户怎么样”
→ 没有限定单一指标，期望得到整体账户评价，属于复杂任务。
```

### 2. 简单任务

简单任务是：**用户提出了明确、有限、可以直接回答的账户事实问题，使用 `summary` 即可完成回答，不需要额外生成 `conclusion`。**

通常同时满足以下条件：

1. 查询对象明确，例如全账户、基金账户、投顾账户、指定产品或自选基金；
2. 回答目标明确，例如金额、持仓、份额、收益、收益日历或归因结果；
3. 时间范围、产品范围等必要参数可以从用户表达中识别，或允许使用已有协议默认值；
4. 每个子问题可以独立回答，不需要解释多个维度之间的关系；
5. 使用最少必要的 MCP 即可取得直接答案；
6. `summary` 能够完整承载本次直接答案，不需要账户级收束。

简单任务示例：

| 用户问题 | 卡片范围 | Summary 要回答的内容 |
| --- | --- | --- |
| “我的账户有多少钱” | ACC-01 | 总资产和账户构成 |
| “我的基金账户怎么样” | ACC-02 | 基金账户的直接概况 |
| “我持有这只基金多少份” | ACC-19 | 指定产品份额 |
| “我都买了哪些产品” | ACC-11 | 持仓列表和直接持仓事实 |
| “我的资产怎么分布” | ACC-12 | 资产、地区或行业分布事实 |
| “我今年收益怎么样” | ACC-13-A | 本年收益结果 |
| “看一下历年收益” | ACC-13-B | 各自然年度收益结果 |
| “哪个月亏得最多” | ACC-14 | 收益日历中的时间明细 |
| “哪些产品拖累了收益” | ACC-15 | 已有归因结果中的主要拖累项 |
| “我的自选基金今天涨跌如何” | ACC-18 | 自选基金当日估值或涨跌事实 |

多个简单问题同时出现，不自动升级为复杂任务。例如：

```text
“我都买了哪些产品，今年赚了多少”
```

虽然会命中持仓结构和收益表现两类卡片，但两个问题可以分别取得事实后直接汇总，不要求解释持仓与收益之间的关系，因此仍可以调用简单 Summary 任务。

简单任务的输出要求：

```text
summary = 查询范围 + 1～3 个关键事实 + 对用户问题的直接回答
```

简单任务的结果结构为：

```text
summary
→ 实际命中的业务 Section 和卡片
```

简单任务不生成 `conclusion` Section，也不得把局部结果扩展成“账户整体健康”“配置合理”或“风险可控”等完整诊断结论。需要继续查看的方向可以放入 `followUp`，不需要为此增加 `conclusion`。

### 3. 复杂任务

复杂任务是：**用户希望得到整个账户的综合评价，或者要求建立多个账户维度之间的关系，`summary` 和 `conclusion` 必须经过诊断、归纳和优先级判断才能回答。**

满足以下任一条件即可判为复杂任务：

1. 用户提出开放式整体问题，例如“我的账户怎么样”“帮我看看账户有什么问题”；
2. 用户明确要求“账户诊断”“全面分析”“账户体检”或“整体评价”；
3. 用户要求综合账户规模、产品持仓、资产结构、收益、超额收益、回撤或收益归因中的多个维度；
4. 用户要求解释维度之间的关系，例如“持仓结构为什么导致收益不好”；
5. 用户要求从多个发现中确定主要问题、主要贡献、主要拖累或关注优先级；
6. 用户的问题不能通过并列陈述若干事实完成，必须形成一个账户级综合判断。

复杂任务示例：

| 用户问题 | 复杂原因 | 诊断重点 |
| --- | --- | --- |
| “我的账户怎么样” | 答案范围开放，期望整体评价 | 结构、收益、风险和归因的综合诊断 |
| “给我的账户做一次全面体检” | 明确要求完整诊断 | 账户总览、持仓结构、收益表现和收益归因 |
| “我的账户主要有什么问题” | 需要比较多个发现并确定优先级 | 找出最重要的结构或表现问题 |
| “持仓结构为什么导致收益不好” | 要求建立结构与收益之间的关系 | 持仓、资产结构、收益和归因的交叉判断 |
| “整体看我的收益和风险是否匹配” | 需要综合收益、超额收益和回撤 | 收益质量与回撤表现的联合评价 |
| “哪些重仓产品是账户的主要拖累” | 需要关联持仓权重和产品归因 | 持仓明细与归因结果的交叉分析 |

对于“我的账户怎么样”这类完整账户诊断，现有输出结构提供的诊断顺序是：

```text
summary
→ account_overview
→ holding_structure
→ return_performance
→ return_attribution
→ conclusion
```

对应的诊断证据可以覆盖：

```text
账户规模和构成
+ 产品持仓及集中度
+ 资产、地区和行业结构
+ 收益、超额收益和回撤
+ 主要收益贡献和拖累
```

复杂任务仍应按实际诊断问题规划 MCP，不表示无条件调用全部 MCP。卡片计划和 MCP 计划继续保持独立：卡片决定前端展示内容，MCP 只为 `summary` 和 `conclusion` 提供本次需要的真实证据。

复杂任务的输出要求：

```text
summary = 诊断范围 + 最重要的账户事实 + 当前核心发现

conclusion = 跨维度综合判断 + 主要关注点及优先级 + 数据边界或后续方向
```

复杂任务只能使用本次 MCP 实际返回且校验通过的证据。数据不足时应降级为局部诊断，明确哪些维度暂时无法判断，不能用 deferred 卡片尚未加载的数据补足结论。

### 4. 简单与复杂的判定顺序

上游大模型按以下顺序判断：

```text
第一步：用户是否明确要求整体账户诊断、体检或主要问题判断？
├── 是 → 复杂任务
└── 否
    ↓
第二步：回答是否需要建立两个或以上诊断维度之间的关系？
├── 是 → 复杂任务
└── 否
    ↓
第三步：多个子问题是否都可以作为独立事实问题直接回答？
├── 是 → 简单任务
└── 否 → 复杂任务
```

补充规则：

- 单张卡片也可能对应复杂任务，例如开放式的“我的账户怎么样”；
- 多张卡片也可能只是多个简单问题的并列展示；
- MCP 失败、空数据或部分可用只影响输出降级，不改变原始任务复杂度；
- 自选基金估值属于独立回答大类，不与账户诊断类卡片混排；
- 跨业务大类问题继续遵守 `primaryAccountIntent` 和现有混排限制，复杂度判断不改变这些协议。

### 5. 上游复杂度输出

复杂度结果属于内部路由信息，不写入卡片结构。建议上游卡片计划同时提供：

```json
{
  "taskComplexity": "simple",
  "complexityReason": "用户询问明确的本年收益结果，不需要跨维度诊断",
  "cards": []
}
```

`taskComplexity` 只允许：

```text
simple
complex
```

代码不重新解释用户语义，只根据该结果调度简单 Summary 任务或复杂账户诊断任务。

## 职责边界

- 上游大模型负责识别用户意图及复杂程度、判断使用哪些卡片，并识别卡片需要携带的参数。
- 上游输出同时包含卡片计划和复杂度结果，供后续代码拼接与大模型任务调度使用。
- `account-diagnosis` 预先定义代码拼接规则、简单任务和复杂诊断任务的执行要求。
- 代码消费上游输出的卡片计划，不重新判断卡片，也不重新解析参数。
- 代码优先完成卡片结构、业务 Section、顺序和固定字段等确定性内容。
- 简单任务调用简单 Summary 大模型任务，使用最少必要的 MCP 直接回答单一问题，不生成 `conclusion`。
- 复杂任务调用复杂账户诊断大模型任务，综合结构、收益、回撤和归因等证据生成诊断型 Summary/Conclusion。
- 简单或复杂不能根据问题字数或卡片数量判断，应根据用户期望的答案范围判断：明确、单点、事实查询进入简单任务；开放、整体、需要综合评价的问题进入复杂任务。
- 例如“我今年赚了多少钱”进入简单任务；“我的账户怎么样”进入复杂任务。
- 所有任务都生成 `summary`；只有复杂任务生成 `conclusion`。两者都不得从尚未加载的 deferred 卡片中推断数据。
- 最终结果由代码统一合并和校验。
- 不改变现有卡片结构定义；MCP 业务数据不写入卡片。部分卡片需要参数时，只写入现有协议允许的参数字段。

## 对现有编排协议的影响

现有 [`AI顾问结果输出与组件编排.md`](../AI顾问结果输出与组件编排.md) 和当前 `compose_result.py` 按“每次账户回答都包含一个 `summary` 和一个 `conclusion`”进行约束。采用本路由计划后，需要调整为：

```text
simple  → 必须有一个 summary，不能有 conclusion
complex → 必须有一个 summary 和一个 conclusion
```

该变化只调整 Section 编排和校验规则，不改变任何卡片结构定义。
