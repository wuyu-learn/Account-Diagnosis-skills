# 用户问题与卡片组合规则修改计划

计划日期：2026-08-01

计划次序：第三阶段（集中用户问题与卡片组合规则）

前置计划：[`复杂账户诊断理念注入优化计划-2026-08-01-02.md`](./复杂账户诊断理念注入优化计划-2026-08-01-02.md)

信息来源：[`AI顾问结果输出与组件编排.md`](../AI顾问结果输出与组件编排.md)

执行条件：第二阶段完成账户顾问工作立场和复杂诊断理念注入后，再实施本计划。

## 1. 当前缺口

当前单卡选择主要位于 `account-card-routing.md`，用户意图和复杂度位于 `account-route-planner.md`。但以下规则还没有集中表达：

- 典型用户问题对应什么卡片组合；
- 多个独立问题如何合并、去重和排序；
- 完整账户诊断默认覆盖哪些卡片；
- 相同卡片组合在什么情况下是 simple、什么情况下是 complex；
- 卡片组合、MCP 计划和最终 Section 各自由谁决定。

结果是单卡容易找到，复合问题和完整诊断仍需要模型从多份文档自行拼接规则。

## 2. 从结果编排文档提取的规则

### 2.1 回答结构

```text
simple
→ summary
→ 实际命中的业务 Section 和卡片

complex
→ summary
→ 实际命中的业务 Section 和卡片
→ conclusion
```

复杂度只决定是否生成 `conclusion`，不改变已有卡片结构。

### 2.2 卡片组合方式

- 每个独立 `subQuery` 先选择精确卡片；
- 多个独立问题合并各自命中的卡片；
- 相同 `cardId` 只保留一次；
- 同一业务类型可以包含多张卡片，每张卡片对应一个 Section；
- 跨业务类型由代码按 `account_overview → holding_structure → return_performance → return_attribution` 排序；
- 账户诊断类 ACC-01～ACC-15 与自选基金类 ACC-18 不混排；
- 编排代码不重新理解用户意图，也不增加或替换卡片。

### 2.3 卡片与 MCP 独立

卡片组合决定前端展示什么，MCP 计划只为 Summary 和 complex Conclusion 提供证据。不能按卡片数量调用同等数量的 MCP，也不能因 MCP 失败删除已选卡片。

## 3. 目标归属

将 `account-diagnosis/references/account-card-routing.md` 设为“用户问题到卡片组合”的唯一规则来源：

```text
account-route-planner.md
→ 识别意图和复杂度
→ 按 account-card-routing.md 输出 cardPlans

account-card-routing.md
→ 维护单卡映射
→ 维护复合问题组合规则
→ 维护完整诊断默认组合
→ 维护卡片参数

account_contract.py
→ 维护卡片固定结构、Section、标题和 narrative
```

`complex-diagnosis.md` 继续只负责诊断路径和 MCP 证据关系，不重复维护卡片组合。

## 4. 计划新增的卡片组合规则

### 4.1 组合原则

```text
拆分独立账户问题
→ 为每个问题选择最具体卡片
→ 合并 cardPlans
→ 去重相同 cardId
→ 只保留 primaryAccountIntent 所属回答大类
→ 代码按固定业务顺序生成 Section
```

不得因为 `taskComplexity = complex` 自动补齐所有诊断卡片。只有用户要求完整账户诊断时，才使用完整诊断默认组合。

### 4.2 典型问题与卡片组合

| 用户问题 | 复杂度 | 卡片组合 |
| --- | --- | --- |
| “我的账户有多少钱” | simple | ACC-01 |
| “我的基金账户怎么样” | simple | ACC-02 |
| “我持有这只产品多少份” | simple | ACC-19；明确产品时按协议填写 `productId` |
| “我都买了什么” | simple | ACC-11 |
| “我的资产、地区和行业怎么分布” | simple | ACC-12 |
| “持仓明细和资产结构都看一下” | simple | ACC-11 + ACC-12 |
| “我今年收益怎么样” | simple | ACC-13-A |
| “看一下历年收益” | simple | ACC-13-B |
| “哪个月亏得最多” | simple | ACC-14 |
| “今年哪些产品在拖累” | simple | ACC-15，`dateType = Y0` |
| “我买了什么，今年赚了多少” | simple | ACC-11 + ACC-13-A |
| “今年收益多少，哪些产品在拖累” | simple | ACC-13-A + ACC-15，`dateType = Y0` |
| “哪些重仓产品是主要拖累” | complex | ACC-11 + ACC-15 |
| “持仓结构为什么导致收益不好” | complex | ACC-11 + ACC-12 + ACC-13-A + ACC-15；“持仓结构”无法进一步区分时同时覆盖明细和结构 |
| “资产和行业配置为什么拖累收益” | complex | ACC-12 + ACC-13-A + ACC-15 |
| “我的账户怎么样” | complex | ACC-01 + ACC-11 + ACC-12 + ACC-13-A + ACC-15 |
| “我的自选基金今天怎么样” | simple | ACC-18，独立回答 |

表中完整账户诊断组合由结果编排文档的完整业务 Section、各意图精确选卡规则和当前诊断能力共同确定。若后续产品要求调整完整诊断覆盖范围，只在 `account-card-routing.md` 修改这一处。

### 4.3 相同组合、不同复杂度

卡片组合不能反向决定复杂度：

```text
“我买了什么，哪些产品在拖累”
→ 两个结果可以独立回答
→ simple
→ ACC-11 + ACC-15

“我的重仓产品是不是主要拖累”
→ 必须关联持仓权重和同周期归因
→ complex
→ ACC-11 + ACC-15
```

Planner 先根据用户是否要求关系判断确定复杂度，再按问题内容选择卡片。

## 5. 文件修改计划

1. 扩展 `account-card-routing.md`：增加目录、组合原则、典型问题组合表、完整诊断默认组合和跨大类处理；
2. 精简 `account-route-planner.md`：保留复杂度和计划输出协议，明确卡片组合只能来自 `account-card-routing.md`；
3. 更新根 `SKILL.md` 的资源说明，将 `account-card-routing.md` 标记为单卡与组合选卡规则；
4. 保持 `account_contract.py` 只维护固定卡片和 Section 契约，不写入自然语言路由规则；
5. 保持 `complex-diagnosis.md` 只维护诊断和 MCP 逻辑，不复制卡片组合表；
6. 不修改 Planner 输出字段、卡片信封或最终 v2.2 JSON。

## 6. 验证计划

增加卡片路由指导协议测试，至少覆盖：

- 单意图精确选卡；
- 同一业务类型的多卡组合；
- 多个独立问题合并卡片后仍为 simple；
- 相同卡片组合可以对应 simple 或 complex；
- 完整账户诊断默认组合；
- ACC-15 `dateType`；
- 重复卡片去重；
- 固定业务顺序；
- 账户诊断类与自选基金类不混排；
- 卡片组合不触发逐卡 MCP 调用。

语义选卡仍由 LLM 完成，测试负责锁定 reference 中的规则和代表性场景；代码测试继续负责校验 cardId、参数、去重、混排和顺序。

## 7. 验收标准

- 查看一个 reference 即可确定典型用户问题对应的卡片组合；
- 单卡、复合问题和完整诊断规则不再分散维护；
- Planner 不在其他位置创造新的卡片组合规则；
- complex 不自动等于“全部卡片”，完整诊断除外；
- 卡片组合与 MCP 计划保持独立；
- simple/complex、卡片结构、Section 固定结构和最终 v2.2 输出均不改变。

