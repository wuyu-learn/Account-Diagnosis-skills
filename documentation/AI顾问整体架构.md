# AI 顾问整体架构

## 文档定位

本文档说明 AI 顾问系统的上层处理链路，以及账户诊断相关 Skills 在整体系统中的位置。账户诊断只是全局场景分发后的一个业务分支。

## 全局三段式流水线

```text
用户查询
→ Global Phase A：路由与实体抽取
→ Global Phase B：按场景分发及业务域处理
→ Global Phase C：结果聚合与编排
→ v2.2 统一响应
```

### Global Phase A：路由与实体抽取

通过语义判断完成：

- 识别一个或多个业务场景。
- 将复合问题拆成可独立处理的 `subQuery`。
- 为场景分配权重并确定主场景。
- 提取基金、基金经理、基金公司、市场主题和策略等业务实体。

#### 主 Agent 的 Route Extract 输出

主 Agent 首先输出完整的场景路由与实体抽取 JSON。以下示例对应用户问题“我都买了哪些产品，今年收益怎么样”：

```json
{
  "scenes": [
    {
      "scene": "问账户",
      "weight": 0.9,
      "subQuery": "我都买了哪些产品，今年收益怎么样"
    }
  ],
  "entities": {
    "fund_names": [],
    "fund_codes": [],
    "manager_names": [],
    "company_names": [],
    "market_subjects": [],
    "strategy_names": []
  },
  "primaryScene": "问账户",
  "isMultiScene": false,
  "orchestration": null,
  "clarify": {
    "needed": false,
    "question": null
  }
}
```

这里的 `isMultiScene` 表示是否命中多个全局业务场景，不表示一个业务域内部是否包含多个二级意图。上述问题虽然同时包含“持仓”和“收益”两个账户诉求，但都属于 `问账户`，因此 Global Phase A 仍输出一个场景；账户域收到请求后再拆分为 `holding_structure` 和 `return_performance`。

LLM 负责语义识别；代码负责补齐缺失值、规范字段、计算多场景标识及确认主场景。
`orchestration` 是下游编排预留字段，在本阶段固定为 `null`；`clarify` 在本阶段固定为 `{ "needed": false, "question": null }`。

### Global Phase B：场景分发及业务域处理

根据 `scenes[].scene` 将子问题分发给对应业务域：

```text
Global Phase B
├── 问账户
├── 问基金
├── 问市场
├── 问策略
└── 问投教
```

多个场景可以并行处理。每个业务域负责自己的意图分类、业务规则、卡片选择和结果生成；具体数据获取方式由该业务域的数据协议决定。当前账户卡片统一使用 `deferred`，由前端组件取数。

#### 主 Agent 分发给子 Agent 的会话格式

主 Agent 使用以下固定会话模板调用目标业务域的子 Agent：

```text
帮我解析并处理和${市场/基金产品/策略/账户/投教}相关的问题：

${json串}
```

其中：

- `${市场/基金产品/策略/账户/投教}` 表示本次分发的目标业务域。
- `${json串}` 必须是 Global Phase A 生成的完整 JSON，不得只传目标场景的 `subQuery`，也不得重新生成或改写。
- 子 Agent 从完整 JSON 的 `scenes[]` 中读取属于本业务域的记录，并保留 `entities`、`primaryScene`、`isMultiScene`、`orchestration` 和 `clarify` 作为上游上下文。
- 同一业务域即使包含多个二级意图，也由该业务域子 Agent 在内部继续拆分，不由主 Agent 提前转换成业务域内部意图。

问账户示例：

```text
帮我解析并处理和账户相关的问题：

{
  "scenes": [
    {
      "scene": "问账户",
      "weight": 0.9,
      "subQuery": "我都买了哪些产品，今年收益怎么样"
    }
  ],
  "entities": {
    "fund_names": [],
    "fund_codes": [],
    "manager_names": [],
    "company_names": [],
    "market_subjects": [],
    "strategy_names": []
  },
  "primaryScene": "问账户",
  "isMultiScene": false,
  "orchestration": null,
  "clarify": {
    "needed": false,
    "question": null
  }
}
```

### Global Phase C：结果聚合与编排

接收各业务域处理结果并生成完整响应：

- 按业务顺序合并内容区块。
- 合并并去重卡片。
- 建立 section 与 card 的关联。
- 生成查询概要、内容衔接、查询收束和后续问题。
- 添加风险提示。
- 输出统一的 v2.2 JSON。

> 当前实现说明：项目尚未提供独立的 Global Phase C 组件。已实现的“问账户”业务分支由 `account-diagnosis` 在账户域内部直接完成结果编排，并输出最终的 v2.2 响应（含 `version`、`meta`、`risk_warning`）；跨业务域聚合暂未实现。账户域内部的 `result-composer` 不属于全局 Phase C，只负责账户域自身的编排与校验。

## 账户诊断的位置

账户诊断位于 Global Phase B 的“问账户”业务分支：

```text
Global Phase A：route-extract
        ↓
Global Phase B：场景分发
        ↓
问账户业务分支
└── account-diagnosis（账户总控入口）
    ├── 账户意图识别模块
    ├── 账户领域内部模块
    │   ├── 资产总览
    │   ├── 持仓结构
    │   ├── 收益表现
    │   ├── 收益归因
    │   └── 自选基金估值
    ├── 生成并归一化卡片计划
    └── 编排并输出账户域最终 v2.2 响应
        ↓
账户域最终 v2.2 响应（version / meta / sections / cards / risk_warning / followUp）
```

账户域内部不要继续使用 Global Phase A、B、C 命名，避免与上层阶段混淆。账户内部步骤可以使用：

```text
Account Step 1：账户意图识别
Account Step 2：卡片选择与计划归一化
Account Step 3：账户域最终编排与 v2.2 输出
```

账户内部不直接获取卡片业务数据。当前所有账户卡片输出为 `dataMode: "deferred"` 且 `data: {}`，由前端组件完成取数。Account Step 3 在账户域内部完成 `summary → 业务 section → conclusion` 的编排，并由 `account-diagnosis` 直接拼接、校验并输出最终的 v2.2 JSON（含 `version`、`meta`、`risk_warning`），不再依赖独立的 Global Phase C。跨业务域聚合不在当前账户域职责内。

账户意图分为两个账户回答大类：账户诊断类（资产总览、持仓结构、收益表现、收益归因）和自选基金类（自选基金估值）。同一大类内的多个意图可在一次账户域结果中按固定业务顺序混排；当一次问账户分发同时包含两个大类的意图时，账户域只处理 `primaryAccountIntent` 所在大类，丢弃另一大类，不为被丢弃的大类生成 section 或卡片。

## 账户诊断卡片定义

账户卡片按“意图大类、对象层级、资产范围”三个维度描述，避免将账户类型、分析能力和持仓层级混为同一分类。卡片编号是既有组件协议的一部分，不连续且不得按表格顺序重新编号。

| 意图大类 | 编号 | 名称 | 对象层级 | 资产范围 | 回答的问题 |
| --- | --- | --- | --- | --- | --- |
| 资产总览 | ACC-01 | 账户总资产 | 全账户 | 全部 | 我一共有多少钱、钱怎么构成 |
| 资产总览 | ACC-02 | 基金账户详情 | 分账户 | 基金 | 基金账户整体怎么样、赚了多少、里面有什么 |
| 资产总览 | ACC-03 | 基金持有详情 | 单产品 | 基金 | 我持有的这只基金整体怎么样 |
| 资产总览 | ACC-19 | 产品份额明细 | 单产品份额 | 基金 | 我在这个产品中持有多少份额 |
| 资产总览 | ACC-04 | 投顾账户详情 | 分账户 | 投顾 | 投顾账户整体怎么样、有几个组合、赚了多少 |
| 资产总览 | ACC-05 | 投顾组合详情 | 单组合 | 投顾 | 指定组合怎么样、赚了多少、买了什么 |
| 资产总览 | ACC-06 | 投顾调仓记录 | 单组合记录 | 投顾 | 指定组合调过哪些仓、什么时候、为什么 |
| 资产总览 | ACC-07 | 货币账户详情 | 分账户 | 货币 | 货币基金账户有多少钱、收益多少 |
| 资产总览 | ACC-08 | 货币持有详情 | 单产品 | 货币 | 我持有的这只货币基金怎么样 |
| 资产总览 | ACC-09 | 专户账户详情 | 分账户 | 专户 | 专户账户整体怎么样 |
| 资产总览 | ACC-10 | 专户持有详情 | 单产品 | 专户 | 我持有的这个专户产品怎么样 |
| 持仓结构 | ACC-11 | 持仓明细 | 全账户持仓 | 全部 | 我都买了哪些、每只怎么样 |
| 持仓结构 | ACC-12 | 资产结构 | 全账户分析 | 全部 | 钱在各维度怎么分布、是否集中 |
| 收益表现 | ACC-13-A | 账户收益总览 | 全账户分析 | 全部 | 我赚了多少、收益怎么样、是否跑赢基准 |
| 收益表现 | ACC-13-B | 账户收益总览 · 分年视角 | 全账户分析 | 全部 | 去年、历年或自然年度收益多少 |
| 收益表现 | ACC-14 | 收益明细日历 | 全账户时间明细 | 全部 | 每天、每月或每年收益多少 |
| 收益归因 | ACC-15 | 收益归因 | 全账户分析 | 全部 | 为什么赚或亏、哪些产品贡献或拖累 |
| 自选基金估值 | ACC-18 | 自选基金估值卡 | 自选列表 | 基金 | 关注的基金今天涨跌如何、净值是否更新 |

### 卡片层级

```text
ACC-01 全账户
├── ACC-02 基金账户
│   ├── ACC-03 单只基金持有详情
│   └── ACC-19 指定产品份额明细
├── ACC-04 投顾账户
│   ├── ACC-05 指定投顾组合详情
│   └── ACC-06 指定投顾组合调仓记录
├── ACC-07 货币账户
│   └── ACC-08 单只货币基金持有详情
└── ACC-09 专户账户
    └── ACC-10 单个专户产品持有详情

横向分析
├── ACC-11 全账户持仓明细
├── ACC-12 全账户资产结构
├── ACC-13-A / ACC-13-B / ACC-14 收益表现
└── ACC-15 收益归因

独立回答
└── ACC-18 自选基金估值
```

### 关键选择边界

- ACC-01 回答全账户整体情况；明确基金、投顾、货币或专户账户时，分别选择 ACC-02、ACC-04、ACC-07 或 ACC-09。
- ACC-09 只表示专户账户整体；用户明确指定单个专户产品时选择 ACC-10。
- ACC-11 表示全账户持仓列表；ACC-03 表示单只基金的整体持有情况；ACC-19 只表示指定产品的份额明细，三者不得互相替代。
- ACC-13-A 用于泛收益、累计收益、滚动区间或基准比较；ACC-13-B 用于去年、历年或自然年度视角；ACC-14 用于日、月、年收益明细或收益日历。
- ACC-16、ACC-17 不在当前卡片清单中，不得生成。
- 账户诊断类卡片（ACC-01～ACC-15）与自选基金类卡片（ACC-18）不得出现在同一个账户域结果中；跨大类时按 `primaryAccountIntent` 所在大类取舍。
- 卡片是前端组件声明，不负责提供数据。编排层不检查卡片是否已有接口或数据，只根据用户意图选择准确的卡片编号。

账户意图和 `subQuery` 负责精确选择卡片编号，标准回复模板负责将选中的卡片组织成完整回答。单个子意图即使只命中一张卡片，也需要放入 `summary → 业务 section → conclusion` 的标准结构；复合问题只生成一个公共 `summary` 和一个公共 `conclusion`，中间按业务顺序编排各卡片。编排层不得重新判断意图、额外增加卡片或替换目标卡片，`section.cardId` 必须与上游选定的 `cardId` 一致。详细规则见 `documentation/AI顾问结果输出与组件编排.md`。

## LLM 与代码的职责

适合由 LLM 完成：

- 场景和意图的语义判断
- 复合问题拆分
- 查询概要、业务说明和查询收束文案
- 跨场景内容衔接
- 后续问题生成

适合由代码完成：

- 字段规范化
- 权重和主场景兜底
- Agent 调度
- JSON 拼接
- 卡片去重
- 引用完整性检查
- Schema 校验

基本原则：

```text
LLM 负责理解与表达
代码负责调度、拼接与校验
```

## 请求上下文

用户身份、会话和鉴权信息不属于语义实体，不应由 LLM 从用户问题中提取或生成。

建议由系统入口提供独立请求上下文：

```json
{
  "requestContext": {
    "userId": "USER-ID",
    "sessionId": "SESSION-ID"
  },
  "query": "我的账户今年收益怎么样"
}
```

处理要求：

- `requestContext` 由可信系统层注入。
- 路由及业务 Skills 只能原样透传，不得生成或修改身份字段。
- 数据获取层使用请求上下文确定账户数据范围。
- 最终对外响应不应返回内部鉴权信息。

## 当前项目边界

当前项目主要覆盖：

- Global Phase A 的场景路由。
- “问账户”业务分支的总控调度、意图识别、卡片选择、取数规则，以及账户域内部的最终 v2.2 结果编排与输出。

当前项目没有独立的 Global Phase C 组件，不负责跨业务域聚合；也不负责其他业务域的具体处理逻辑、用户认证、权限校验、接口网关或前端组件实现。
